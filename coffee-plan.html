Coffee Workshop Build Plan

A Vietnamese roastery and café selling western pastries (croissants, carrot cake, kouign-amann) and coffee blends to customers who mostly read it with western eyes. The plan leads with the storefront — the five seconds that decide whether you're credible — then handles bean & blend e-commerce, ZaloPay/MoMo checkout, nationwide shipping, fresh-cake handoff to GrabFood, a teacher-led online school, and a light multi-site admin. The POS owns in-store sales and best-sellers and we leave it alone; the roastery is a separate world. Default language is Vietnamese with a language switch. All heavy services sit behind one swappable interface each, so you start free and upgrade by changing a file, not a refactor.

Part one

What's settled, whatever else happens

None of this depends on the POS. The POS owns in-store; we own online. It's true for two sites and for five.

Do you need a separate backend service?
No — and not because it's small. Because the two heavy jobs, payment and video, both bypass your server entirely.

Students, enrollments, stock, roast batches and sales facts are tables and forms. A NestJS process in front of them adds a network hop and a second deployment while making none of it easier. Card data goes to ZaloPay, MoMo or Stripe's own page; video bytes go browser-to-CDN. Your server moves IDs and short-lived tokens — exactly what Next.js route handlers are good at. Every external provider — payment, courier, video, email, auth — sits behind one small interface (see Part six), so today's free pick and tomorrow's paid pick reach your code through the same call. Revisit only if you pass three developers, need long-lived websockets or heavy CPU, or gain an API consumer that isn't your own product.

Who owns which truth

The most important decision in a multi-system setup. Two systems both believing they own stock is how you end up with numbers nobody trusts.

System Owns — the source of truth Must never own

The app and the POS touch different surfaces of the same business. They never both believe they own the same number.

Part two

The POS — out of scope, by design

Your POS already handles in-store sales, best-sellers and busiest hours per site, and it does it well. So the app does not extract, store or report on POS data. There is no SalesFact table, no nightly rollup, no cross-channel report, no scenario A/B/C/D decision, and no blocked phase. The one rule that survives: the app is a consumer of the POS, never a competitor to it. If the POS exposes an API and you one day want a combined number, you import into a throwaway analytics table then — never into your operational tables.

What does the app own, then?
Only what the POS does not: the storefront, courses, students, online bean and blend orders, bakery items, shipping, and staff tools for those things.

In-store cash, receipts and per-site ingredient depletion stay on the POS. The app never writes a sale, never tracks milk, never ranks best-sellers from the till. Removing the POS integration is roughly a week and a half of work eliminated from the build, and one open question retired before this week's pre-code list.

Part four

The coffee catalog — blends and stock, no roastery

You sell coffee; you don't track the roaster. So the app keeps only what the shop needs: the blend (name, origin, roast level, tasting notes), the bag (weight, grind options, price in VND and USD), the roast date printed on the bag, and how many bags are in stock. There is no RoastBatch, no GreenLot, no yield, no ledger of movements. Stock is a count the staff update by hand — the same way you count bags on the shelf.

What the catalog holds

  • ›Product row per blend: name, slug, origin country, roast level (light/medium/dark), tasting notes.
  • ›Bag options — weight (250g/1kg), grind (whole / espresso / filter / phin) — stored once, selected at the card.
  • ›roastDate as a plain date the staff set when they shelf a batch. The card shows "roasted 3 days ago".
  • ›stock as an integer. Low-stock alert below a threshold. No append-only ledger.
  • ›featuredUntil timestamp rotates the home card without anyone touching code.

What it deliberately doesn't hold

  • ›Green-lot cost, supplier, weight. Out of scope — the roastery is a separate world.
  • ›Yield, batch numbers, operator, profile. None of these reach the storefront or the reports.
  • ›Inter-site transfers as a ledger. Beans move; you just set the per-site stock count by hand.
  • ›True cost-per-kilo calculations. Price is a number the business sets; the app stores it, it doesn't derive it.

Staff touches stock, nothing more

  • ›One form: "I just shelved N bags of Da Lat washed, roast date X" — sets stock and roastDate.
  • ›One drawdown: an online order decreases stock by the line quantity. That's it.
  • ›No negative-stock write happens silently — a checkout that would oversell blocks and the staff see the alert.
The cost this removes
The roastery module was the longest single phase in rev 3 — about a week and a half of specialised mobile logging, yield maths and a stock ledger. Removing it removes the module, the data model for batches and lots, and the report that justified it. You keep only "shop stock of blends", which is a column on Product.
Part five

The storefront — first impression and featured items

You're a Vietnamese roastery and café selling western pastries to customers who mostly look with western eyes. The home page is the five seconds where they decide whether you're a real bakery or a hobby. Lightweight and photograph-led, not feature-packed — the back office can stay rich, but the public site must stay fast.

What is the homepage actually for?
To make a stranger believe, in five seconds, that a real bakery and roastery stands behind it — not to list everything you sell.

Most café sites fail this test by front-loading the menu, the address, the WhatsApp button and a chat widget. Yours should show one strong image, one line of English copy that names the craft ("Roasted in Da Nang. Baked at 5am."), and three featured items. Everything else is a click away. Performance — measured as LCP under 2.5s on a mid-range Android over 4G — is part of the brief, not a polish task.

Three jobs the home page must do

Show, don't list

  • ›One weighted hero photo — a pour, a croissant stack, or a roast drum — at most 60 KB WebP.
  • ›Three featured cards below it, rotating daily: a coffee blend, a bakery item, a class.
  • ›No full menu table on the homepage. Menu is its own /menu page, statically generated.
  • ›No auto-play video anywhere above the fold. Lottie or subtle CSS only.

Establish the brand

  • ›One tagline, English-first with a Vietnamese accent: place name, craft verb, time.
  • ›One roastery photograph with a caption carrying the roast date.
  • ›One small map or three-dot strip showing the sites — proves you're physical, not drop-ship.
  • ›Restraint is the signal of craft: white space, two type sizes, one accent color.

Make it easy to do something

  • ›One primary call-to-action visible without scrolling. Pick from: Order beans, Book a class, Find a café.
  • ›Sticky slim header — 48 px — collapsing to a single word-mark on scroll.
  • ›Cart accessible from a header icon, never a full-screen drawer on first paint.
  • ›Order again for returning customers: a recognised device sees a one-tap reorder.

Featured items — coffee, bakery, blends

Featured items are curated rows, not a product grid. Four to six cards visible, the rest behind "View all". Each card carries a real photograph, a price in VND and USD, and roast date or bake time — the data points that signal freshness over commodity.

Coffee blends

  • ›3–4 featured single-origin or blend Product rows with roast date on the card.
  • ›Roast of the week rotates from a featured_until timestamp — no manual swap.
  • ›Grind selector (whole / espresso / filter / phin) on the card, not buried in detail page.
  • ›Ships nationwide via in-app checkout + courier (Part six).

Bakery — western pastries

  • ›Croissant (plain, almond, chocolate), kouign-amann, pain au chocolat, carrot cake, cinnamon scroll.
  • ›Photograph-led, "baked at 5am", sell-out by noon — urgency is the brand promise.
  • ›Each item carries a bakes_at and siteId; freshness badge resolves on the client.
  • ›Fresh pastry is pickup-only or GrabFood handoff within the local hot zone.

Featured class

  • ›One in-person workshop card on home: title, next date, site, one seat left (real scarcity, not fake).
  • ›One online course card: thumbnail from Cloudflare Stream, "Watch a free preview" button to lesson 1.
  • ›Both deep-link to a single checkout at the same pay() interface.

Performance budget — the part that protects traffic

A slow site loses customers before they see the croissants. You asked for lightweight; this is what that means in numbers a developer can hold the line on.

Targets (mid-range Android, 4G)

  • ›LCP < 2.5 s, CLS < 0.1, INP < 200 ms on the home and product pages.
  • ›Initial JS bundle < 150 KB gzipped. No UI kit shipped in the home route.
  • ›Hero image < 60 KB WebP, AVIF with WebP fallback.
  • ›Page weight < 600 KB on first paint for any storefront route.

Mechanics that meet it

  • ›Static storefront routes via Next.js generateStaticParams + ISR for stock-sensitive pages.
  • ›next/image with priority on hero only; everything else lazy.
  • ›Cart is a tiny client island; the page around it is server-rendered and cached.
  • ›No parallax libraries, no scroll-jacking, no full-bleed hero video, no chat widget above the fold.

Heavy but isolated

  • ›The course player route is allowed to be heavy — few visit it, and they're enrolled already.
  • ›Video player (Cloudflare Stream or YouTube unlisted) loads only on the lesson route.
  • ›Admin staff area is a separate segment; never let its heavy widgets touch the public bundle.
  • ›Route-level code splitting is mandatory; see "What goes wrong" risk 12.
The voice problem
Vietnamese, written in English, that reads as western craft — not as an apology for being in Vietnam.

Most Vietnamese café sites in English sound either defensive ("we serve authentic…") or generic ("the best coffee in town"). Neither makes a western visitor feel they've found a real roastery. Say where, when, and what's fresh. Show the roast date, the bake time, the origin. Skip superlatives; the photographs are the superlatives. Two typefaces — a clean grotesk for headings, a readable serif or grotesk for body — and one accent in tobacco or terracotta does more for credibility than any mission statement.

The mood — authentic, nostalgic, a touch of west in Vietnam

The brand isn't trying to look like a Saigon startup or a Brooklyn coffee bar. It's a small Da Nang family that roasts and bakes, and that's the feeling every screen should hand a visitor in the first two seconds. Nostalgic, charming, rooted — with a western accent the visitor already recognises (the croissant, the carrot cake), and a current-trending touch so it doesn't feel like a museum. Below is the concrete version of that mood — the colour, the photography, the copy, and how to keep it from sliding either into corporate-neutral or into kitsch.

Palette — warm paper, not white

  • ›Paper #F2F1EC as the page background (already in this doc's CSS). Never pure white — pure white reads as SaaS, not bakery.
  • ›Ink #1E1A17 for type — a warm near-black, softer than #000 and warmer than zinc.
  • ›Terracotta #A8642E as the single accent. Tobacco and roast-crust tones for secondary.
  • ›One cool tone allowed only as a success indicator (the ok #4E7A4A) — never as a brand colour.
  • ›Gradients forbidden. A flat warm palette is the nostalgic signal.

Photography — film, not phone-corporate

  • ›Shoot on a 35mm or a film-emulation preset, not on a clean white studio sweep. Slight grain, marginal contrast, real light through a window.
  • ›Hands in frame — a baker's hand on a tray, a pour, a scoop of beans. Hands are the family-and-craft signal.
  • ›The shop, not a set: worn counter, the roaster, the chalk board menu, a stack of burlap sacks. Imperfection is the point.
  • ›Crop tight — the crumb of the croissant, the bloom on a pour, the dust on a sieve. Tight crops read as craft; wide shots read as stock.

Copy — family reunion, not slogan

  • ›Us, we, our family. "We started roasting in our Da Nang kitchen in 2017" beats "Authentic coffee since 2017." People remember the kitchen.
  • ›Specific Vietnamese place names — Da Nang, Hội An, Đà Lạt, the Central Highlands. Specificity is the antidote to "authentic."
  • ›One anecdote per page, not a manifesto. The home page gets the founding line; the about page gets three more, never five.
  • ›Bilingual respect: Vietnamese comes first, English is the second voice, not the correction of the first. Layout treats them as equal.

A touch of the west, planted in Vietnam

  • ›The western items (croissant, kouign-amann, carrot cake) are named in their western names, with a Vietnamese subtitle. Don't rename kouign-amann to "bánhBreton" — the foreign name is part of the charm.
  • ›Roast levels in English (light / medium / dark) with the Vietnamese alongside. Origin countries in both.
  • ›The English isn't subordinate and the Vietnamese isn't shy. They sit beside each other the way they do on a real Da Nang chalk board.
  • ›A tiny detail only a real roaster has — the roast date printed on the bag, the baker's initials on a cake box — anchors the "this is a real place" feeling.

Trending, but grounded

  • ›Borrow one current trend at a time and make it earn its place. Spring 2025 examples: oversized type set tight, a single hand-drawn illustration in the footer, a "stock-of-the-week" rotating card.
  • ›Don't borrow trendy motion — no scroll-triggers, no parallax, no rubber-banding. Motion is exactly where "nostalgic" turns into "gimmick."
  • ›Borrow the aesthetic of newsletters / Substack-style typography: a comfortable measure, generous leading, serif display. Quiet, slow, read-not-glanced.
  • ›Quarterly: refresh the one trending element. If it stops trending, swap it. The base palette and photography never trend — that's why they last.

What to avoid — the kitsch line

  • ›No propagandist Vietnamese iconography (cone hats, red flags, water puppets). Real nostalgia is daily objects — enamel mugs, wooden trays, a tin of beans — not postcardVietnam.
  • ›No fake-vintage fonts (no "handwritten" display faces). Fraunces' soft terminals give the warmth without the costume.
  • ›No "as featured in" placeholder logos. Credibility comes from the roast date and the photographs, not from invented press strips.
  • ›No autoplay, no auto-rotating carousel faster than 8s. Trendy ≠ busy; nostalgic ≠ stuck.
The single feeling the home page should leave
"I want to walk into this place on a Sunday morning and sit with my family."

Every decision — paper background, terracotta accent, hands in frame, the founding line in Vietnamese first, the croissant labelled in its own name, the roast date on the bag — is in service of that feeling. If a proposed element doesn't move the visitor closer to it, it's decoration and it doesn't ship.

Default Vietnamese, free fonts, one switch

The app opens in Vietnamese by default and a header toggle flips the whole site to English in one tap. Every string goes through next-intl from the first commit — a hard-coded English word in a component is a bug, not a polish task. The two typefaces are free and both render Vietnamese diacritics correctly out of the box; that is non-negotiable, because broken diacritics destroy trust faster than any other visual defect.

Two free typefaces

  • ›Fraunces (Google Fonts, free, SIL) for display — an open-source "soft" serif with full Vietnamese support. Reads as craft bakery, not corporate.
  • ›Be Vietnam Pro (Google Fonts, free, SIL) for body and UI — designed for Vietnamese diacritics, modern grotesk, light weight on the bundle.
  • ›Two weights each, one accent colour. No italic unless a price needs emphasis.
  • ›Self-host as .woff2 subsetted to Vietnamese + Latin — keeps the bundle under the 150 KB JS budget from the perf section.

i18n mechanics

  • ›next-intl middleware sets locale from Accept-Language, defaulting to vi for any VN IP and falling back to vi otherwise.
  • ›Strings live in /messages/vi.json and /messages/en.json; nothing else holds copy.
  • ›Header toggle sets a cookie and re-renders the route. No reload, no layout shift.
  • ›Date and currency format through the i18n layer: VND for vi, USD shown alongside for en.

What "exotic" means here

  • ›Not a novelty typeface — a craft typeface. Fraunces' high-contrast curves and soft terminals signal artisanal bake, not gimmick.
  • ›The Vietnamese itself is the local accent; the typography is the craft accent. Both support diacritics, both are free.
  • ›One display serif + one grotesk + one terracotta accent is the whole system. Adding more is what makes a site feel heavy.
Part six

Pluggable providers — pay and ship now, swap later

Today's budget is zero and tomorrow's will not be. Every external service — payment, courier, video, email, auth — is hidden behind a small interface with one adapter per provider. The first implementation ships on the cheapest credible option; every later upgrade is a new adapter file plus an environment variable, never a rewrite of pages or data flows.

The one rule that makes "start free, upgrade later" actually work?
Pages and route handlers call the interface, never the provider. pay(), not zaloPay(). ship(), not ghnShip().

If the provider's name appears anywhere outside its own adapter file, you've coupled the product to the vendor and a swap becomes a refactor. The interface owns the verb; the adapter owns the noun. A factory reads an env var and returns the active adapter. New provider = new file registered in one place. Existing pages do not change.

What the adapter files look like

The interface (one per concern)

  • ›A TypeScript interface with 2–5 methods. No types from the provider leak out.
  • ›Returns plain types the rest of the app already uses — PaymentResult, Shipment, VideoToken.
  • ›Lives in /lib/providers/<concern>/types.ts.

The adapter (one per provider)

  • ›Implements the interface. The only file that imports the provider's SDK.
  • ›Owns webhook parsing and signature verification — never lets provider JSON reach a page.
  • ›Lives in /lib/providers/payment/zalopay.ts, …/momo.ts, etc.

The factory (one line that picks)

  • ›getPaymentProvider() reads process.env.PAYMENT_PROVIDER and returns the right adapter.
  • ›Supports a list for multi-provider — ZaloPay for locale VN, card for locale EN.
  • ›The only place that knows more than one adapter exists.

Payment routing — local vs international

The interface takes a routing hint so you can run two providers in production without a flag day. Vietnamese orders prefer ZaloPay and MoMo; international students buying an online course fall back to card.

Default routing

  • ›locale=vi or shipping address in VN → ZaloPay then MoMo.
  • ›locale=en or billing address outside VN → card (PayOS sandbox now, Stripe later).
  • ›Student can override on checkout — never collapse the choice.
  • ›One webhook handler per provider, all writing the same Order row.

What never changes

  • ›Order.id, Order.status, Order.total are provider-agnostic.
  • ›Receipts and certificates read from Order, never from provider payloads.
  • ›Refunds go through the same interface — refund(order, amount, reason).

How Vietnamese sites actually pay — and we mimic it

We don't invent the checkout. We copy what Tiki, Shopee VN, The Coffee House and Phuc Long already trained every Vietnamese phone to expect — because customers who recognise the flow pay without friction, and customers who don't, leave. The pattern below is the default vi checkout; en follows the same shape with one panel swap.

Page 1 — the method picker

  • ›A vertical list of tiles, not a dropdown. Each tile: logo, name, "Miễn phí" or the fee in VND.
  • ›Order for a VN address shows in this order: ZaloPay, MoMo, VNPay QR (ATM + QR interbank), bank transfer (Vietcombank, Techcombank…), card (Visa/MC/JCB), COD.
  • ›One radio per row. A sticky bottom bar shows the total in VND and the CTA "Thanh toán" / "Pay".
  • ›No card form on this page — card data is never on our domain. Choosing card moves to step 2.

Page 2 — the redirect or the QR

  • ›ZaloPay / MoMo on mobile: tap "Thanh toán" → the ZaloPay or MoMo app opens via app-link with the amount prefilled. User confirms in their app, returns to ours.
  • ›ZaloPay / MoMo on desktop: a QR code renders in-page. User scans with their phone app, pays, the page shows "Đang xử lý…" and auto-advances on webhook.
  • ›VNPay QR / bank transfer: a static QR with the order amount and reference. Same "Đang xử lý…" polling screen.
  • ›Card: leaves the site to PayOS / Stripe's hosted page. Returns to our /checkout/return with a session id.
  • ›COD: no redirect. Order is created with status = awaiting_cod, receipt email goes out, staff see it in the queue.

Page 3 — the confirmation

  • ›A short "Cảm ơn" page: order number, what they bought, when it ships, a track-shipment link for beans, a download-receipt button.
  • ›Polling the webhook has a 30s timeout. If it doesn't arrive, the page shows "Đang xử lý — chúng tôi sẽ xác nhận trong ít phút" instead of pretending it's done.
  • ›Resend sends the receipt; the "my orders" page reads Order, not the provider payload.
  • ›Never own the card number; never own the QR. We render what the gateway hands us and we listen for the webhook.
The one Vietnamese pattern most western sites miss
COD — cash on delivery — is the second-most-used online payment method in Vietnam, behind only e-wallets. Skip it and you lose bean customers who trust cash more than an app.

Add a COD lane to getPaymentProvider: it returns a PaymentResult with provider = 'cod', no redirect, no webhook. Order.status starts awaiting_cod and the staff queue drives it to completed when the courier collects. Same interface, one extra enum value — no new code paths in the storefront.

Shipping — two lanes, one interface

Beans and blends ship nationwide; fresh cakes don't. Each lane uses the same CourierProvider interface where it can, and a narrower LocalHandoff interface where the local partner doesn't talk to your backend yet.

∪ Lane 1 — Beans & blends (nationwide) in-app, end to end
Flow
Customer pays in-app (ZaloPay/MoMo) → order is paid → createShipment via GHN → tracking written back → customer gets a tracking link + email.
Why in-app
Beans keep, ship anywhere, full control of UX and data. This is the lane that scales and that you report on.
Start cost
GHN API is free per-shipment. No monthly fee.
Upgrade path
Add Ahamove (same-day in HCMC/HN) and ViettelPost (remote provinces) as new CourierProvider adapters. Pick by destination postcode.
Verdict: build the full in-app shipping flow now. It's the revenue lane that's already nationwide.
∪ Lane 2 — Fresh cakes & pastries (local hot zone) handoff today, owned later
Flow now
Customer taps "Order for delivery" on a pastry card → deep link into GrabFood merchant page (or ShopeeFood) where they finish. You never see payment or address.
Why handoff
Cakes don't keep, the hot zone is small, and Grab owns the courier network you'd otherwise rebuild.
What you lose

Part nine

What goes wrong

Roughly in order of damage done.

01

Building anything that assumes two sites

Every product, bakery item, staff member, menu item and class session needs a site. Retrofitting that column across a live schema is the most expensive mistake available to you right now, and you have a deadline named "site three."

02

Duplicating what the POS already owns

If the POS already tracks best-sellers, busiest hours, cash and ingredient depletion, let it. The moment the app also writes one of those, two systems track it and nobody trusts either number.

03

Reaching for roastery data the app doesn't need

You removed the roastery module on purpose. Don't let it creep back in as a "small" feature — green-lot cost, yield, batch numbers, operator. Each one re-introduces a ledger, a mobile log form nobody fills in, and a report that justifies the ledger. The catalog only needs a roast date on the bag.

04

Hard-coded copy in a component, any component

A Vietnamese-only string wedged into a JSX file is the slow death of the language switch. From commit one, every word goes through next-intl and /messages/{vi,en}.json. A reviewer should reject any string not in a message file, even "Add to cart."

05

A font that breaks Vietnamese diacritics

Vietnamese carries heavy stacking diacritics. A "pretty" display face without full Vietnamese support renders every menu item broken — and trust dies before the croissant loads. Both fonts in the type system must be verified on a real VN copy paragraph, not only on Latin sample text.

06

Importing a provider's SDK outside its adapter file

The moment a page calls zaloPay() instead of pay(), you've coupled the product to ZaloPay. Adding Stripe, MoMo or anyone else stops being "a new file" and becomes a refactor that touches pages, tests, and types. Rule: the provider's name appears in its adapter file and nowhere else.

07

A heavy storefront that punishes the traffic it's trying to earn

Auto-play hero video, a chat widget above the fold, parallax libraries, a full UI kit shipped to the home route, and 5 MB of unoptimized bakery photos — each one steals from LCP, and customers leave before the croissant loads. Hold the budget in Part five or pay for it in bounced visitors.

08

Generic English that reads as "another Vietnamese cafÃ© site"

"We serve the best coffee in town" and "authentic western pastries" both signal the opposite of craft to a western visitor. Lead with place, time, and what's fresh — roast date, bake time, origin — and let the photographs be the superlatives.

09

Putting the bakery on the same shipping lane as the beans

A croissant that spends a day with GHN is a soggy croissant. Nationwide bean shipping and local hot-zone cake handoff are two lanes belonging to two interfaces — never one shipping page that pretends they're the same.

Part eleven

The six provider interfaces — the actual contract

"Write down the six verbs" turned out to be the unclear one — so here they are, written. Copy each interface into /lib/providers/<concern>/types.ts as-is. The adapter files implement them; the pages call them; nobody outside an adapter file imports a provider SDK. That single rule is the whole reason "start free, swap later" survives.

Where they live

/lib/providers/ payment/ types.ts # PaymentProvider interface + PaymentResult, Routing zalopay.ts # imports ZaloPay SDK — nowhere else does momo.ts # imports MoMo SDK payos.ts # card sandbox, later Stripe index.ts # getPaymentProvider(routing) → adapter courier/ types.ts # CourierProvider + Shipment ghn.ts # nationwide bean lane grabexpress.ts # later — hot-zone cake lane index.ts # getCourierProvider(lane) → adapter local-handoff/ types.ts # LocalHandoff — the GrabFood deep-link today grabfood.ts video/ types.ts # VideoProvider + VideoToken youtube.ts # free-preview lessons (unlisted) cloudflare.ts # paid lessons (Stream signed playback) index.ts email/ types.ts # EmailProvider resend.ts auth/ types.ts # AuthProvider clerk.ts

The folder is the contract. A page that needs to charge writes getPaymentProvider(routing).pay(...), never zaloPay(...). A new provider is a new file plus one line in the relevant index.ts — not a refactor.

1. PaymentProvider — ZaloPay, MoMo, card, later Stripe

// /lib/providers/payment/types.ts
export type PaymentMethod = 'zalopay' | 'momo' | 'vnpay_qr' | 'bank_transfer' | 'card' | 'cod'

export interface Routing {
  locale: 'vi' | 'en'
  addressCountry: string          // ISO code; gates the default method
  preferredMethod?: PaymentMethod  // student override on checkout
}

export interface PaymentResult {
  provider: PaymentMethod
  providerRef: string            // the gateway's order id — written to Order.providerRef
  redirectUrl: string            // browser leaves to the gateway's hosted page
}

export interface PaymentProvider {
  // Create a charge on the gateway; return a redirect URL the browser follows.
  // COD returns an empty redirectUrl and provider='cod'; the page creates the order directly.
  pay(amountVnd: number, orderRef: string, routing: Routing): Promise<PaymentResult>
  // Verify a webhook signature and return a normalised status the page can switch on.
  // COD has no webhook; the page falls through to Order creation immediately.
  parseWebhook(rawBody: Buffer, headers: Record<string, string>): { providerRef: string; status: 'paid' | 'failed' | 'pending' }
  // Refund all or part of an order, through the same gateway that took it.
  refund(providerRef: string, amountVnd: number, reason: string): Promise<void>
}

The factory — one line that picks, in one place

// /lib/providers/payment/index.ts
import { ZaloPayAdapter } from './zalopay'
import { MoMoAdapter }   from './momo'
import { PayOSAdapter }   from './payos'
import type { PaymentProvider, Routing } from './types'

export function getPaymentProvider(routing: Routing): PaymentProvider {
  const method = routing.preferredMethod ?? defaultMethod(routing)
  switch (method) {
    case 'zalopay': return new ZaloPayAdapter()
    case 'momo':   return new MoMoAdapter()
    case 'card':   return new PayOSAdapter()
  }
}

function defaultMethod(r: Routing) {
  if (r.preferredMethod) return r.preferredMethod
  // Vietnamese addresses and vi locale get ZaloPay; everything else card.
  return r.addressCountry === 'VN' || r.locale === 'vi' ? 'zalopay' : 'card'
}

That switch is the only place in the codebase that knows two payment providers exist at once. Adding Stripe is a new stripe.ts and a case 'stripe' here. Every page, every webhook handler, every receipt — unchanged.

How a page actually uses this
Three lines. The provider's name never appears. 
// app/checkout/route.ts — the only payment code on the page
const provider = getPaymentProvider(routing)
const result = await provider.pay(totalVnd, order.id, routing)
redirect(result.redirectUrl)

A reviewer rejection rule, written once and held forever: if zalopay, momo, ghn, clerk, resend, or cloudflare appears anywhere outside its own adapter file, the PR does not merge. That rule is the contract. The interfaces above are what make it enforceable.
